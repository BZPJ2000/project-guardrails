# 变更影响：改这里之前先看那里

"改了 A 坏了 B"的根因是没有一张写明影响面的表，只能靠记忆。每个部件文档末尾必须有一张。

## 影响清单格式

```markdown
## 变更影响
| 改什么 | 必须同时检查 | 必须重跑的测试 |
|---|---|---|
| 优先级字段 | docs/contracts/algo-tasks.md、前端排序展示 | algo/sortTaskPriority |
| params 范围 | 前端校验、后端入库约束 | 全部 algo 单元 |
| 接口返回结构 | 契约版本、前端解析、后端 DTO | 集成测试 |
```

三列的语义：改左边 → 看中间（是否同步）→ 跑右边（是否还绿）。

## 改动前的动作

1. 在 `docs/module-map.md` 定位到部件。
2. 读该部件文档的「变更影响」，列出本次实际触发的行。
3. 把清单写到 `.agent/changes/<YYYY-MM-DD>-<slug>.md`：

```markdown
# 变更：调整优先级权重
触发的影响行：params 范围
计划改动：params.schema.json / 契约 range / 前端校验
计划重跑：algo 全部单元 + 集成测试
未覆盖风险：前端只做了类型校验，未做范围校验
```

4. 按清单改，改完跑门禁。

## 改动后的动作

- `gate.py all` 必须通过。
- 触发行的测试必须重跑并刷新证据（旧证据会被判过期）。
- 更新部件文档的「最后更新」，一句话写清改了什么。

## 回归范围的最小化

不是每次都全量：

| 改动类型 | 最小回归 |
|---|---|
| 纯内部实现（契约不变） | 该单元 + 直接调用它的单元 |
| 契约加字段 | 该单元 + 所有读取该契约的单元 |
| 契约改语义/删字段 | 全量 |
| params 变化 | 所有消费该参数的单元 |
| 目录/命名调整 | 全量 + 部署流程复核 |

拿不准就全量。全量很慢，但比重上线发现坏了好。

## 反向检查

改动完成后问一次：**"我改的东西，有没有谁在依赖它的某个假设？"** 依赖假设的例子：假设字段顺序稳定、假设数组非空、假设时间戳单调、假设 ID 唯一。这些假设不进契约就会被打破，所以要么写进契约，要么写进部件文档的「不变量」。
