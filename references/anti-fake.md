# 反作假：真相源与三层校验

AI 造假的典型形态是"改结果、不改过程"：字段变了，但产生该字段的计算从未运行。防线不是提醒它别撒谎，而是让"直接改结果"在结构上不可行、在门禁上必然失败。

## 唯一真相源（SSOT）表

每个部件文档必须有一张，写在「责任边界」之后：

| 数据 / 字段 | 生产者 | 可写 | 只读 | 变更途径 |
|---|---|---|---|---|
| `task.priority` | 人 | 人 | 算法 | 改 `params.json` 后重跑 |
| `task.scheduleSeq` | 算法 | **算法** | 前端 | 重跑 `algo/sortTaskPriority` |
| `dailySummary` | 后端 | 后端 | 前端 | 调 `POST /summary/rebuild` |

规则：

- 一个字段只能有一个生产者。写两个就是双份真相，必然漂移。
- 「变更途径」写的是**动作**，不是"改数据库"。途径里出现 `UPDATE`、`直接编辑`、`手工改` 即视为设计缺陷。
- 派生字段（上表第二行）在契约里标 `derived: true` 并写明 `producedBy`。

## 派生字段的硬约束

1. 代码里，派生字段只能由声明单元的返回值写入。任何旁路赋值都要在 code review 中被拒。
2. 测试必须包含**反例**：尝试直接写派生字段，系统必须拒绝或忽略并报 `E_DERIVED_READONLY`。
3. 门禁检查 `producedBy` 指向的单元存在且有合格证据（见 `testing-evidence.md`）。**派生字段的证据缺失，等于该字段未被证明**。

## 三层校验

输入进来先过三层，任何一层失败就返回错误码，不进入计算：

```text
结构校验   字段名 / 类型 / 必填 / 未知字段拒绝        → E_CONTRACT_VIOLATION
范围校验   数值在 range 内、单位匹配、数组长度合法     → E_OUT_OF_RANGE
语义校验   业务不变量（无重复、全覆盖、顺序单调等）    → E_INVARIANT_BROKEN
```

输出返回前再过一遍：字段齐全、类型正确、范围正确、不变量成立。**任一条不通过就报错，不返回部分结果，不返回空对象假装成功。**

## 未知即停

缺信息时只有两个合法动作：

1. 问人，并把问题写成一条待办。
2. 在 `params/` 留 `__TBD__` 并让门禁阻断。

没有第三个动作叫"我先给个合理默认值"。数值、阈值、尺寸、权重、超时——全部属于业务决定，实现者无权代填。

## 六个作假信号（自查用）

出现任意一条，停下来核实，不要继续汇报"完成"：

1. 说"已经更新了"某派生字段，但没跑产生它的单元。
2. 说"测试通过"，但找不到证据文件，或证据比代码旧。
3. 数字没有出处：不是来自 params，也不是来自计算结果。
4. 改了实现，但契约文档和部件文档没动 —— 说明变更没走完。
5. 为了让测试变绿而改断言、放宽范围，而不是修实现。
6. 用 mock / 假数据跑通链路，却宣称链路可用。

## 汇报格式（固定四项）

```text
changed:   改了哪些文件，一句话说清每个文件的意图
verified:  跑了什么命令，退出码，证据路径
evidence:  tests/evidence/<date>/<runId>/<unit>.json
risk:      未验证的部分 / 已知不确定点（没有就写"无"）
```

缺 `evidence` 就不许写"完成"，只能写"已改，未验证"。
