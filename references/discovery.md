# 开工前：先查，再借，最后才造

不重复造轮子的前提是**先知道轮子在哪**。新技能落在 `~/.agents/skills/` 下会自动出现在会话的技能目录里，但目录只给一句话摘要 —— 需要一个带「什么时候用」的索引。

## 三步顺序

1. **查本地**：看技能索引 `~/.agents/SKILLS-INDEX.md`，或直接翻 `~/.agents/skills/`。
2. **查网上**：本地没有，用 `web_search` 找现成 skill / 库 / 模板；找到就装，不要自己从零写。
3. **才自己写**：确实没有，再动手，并且写完后立刻登记（见下）。

判断借用还是自建：

| 情形 | 做法 |
|---|---|
| 已有技能覆盖 80% | 借用 + 在项目文档里写"本项目对该技能的偏离点" |
| 已有技能只覆盖一个子问题 | 借用那部分，其余自建 |
| 技能之间存在冲突规则 | 停下来问人，不要自己裁决 |

## 新技能登记（每次都要做）

```bash
python ~/.agents/skills/project-guardrails/scripts/skill-index.py
```

它扫描技能根目录，读每个 `SKILL.md` 的 frontmatter，重写 `~/.agents/SKILLS-INDEX.md`：

```markdown
| 技能 | 一句话 | 什么时候用 |
|---|---|---|
| project-guardrails | 多部件项目防作假治理 | 开新项目 / 改这里坏那里 / 怀疑 AI 编数据 |
| feature-modular-structure | 功能模块化与目录规范 | 目录怎么放、怎么切功能 |
```

「什么时候用」这一列必须写**触发场景**，不是功能描述 —— 它决定下次能不能被想起来。

## 登记之后

- 索引是全局的，所有项目共用；不要为单个项目造私有技能（除非它真的只服务这个项目，那就放项目内 `.agent/skills/`）。
- 两个技能规则冲突时，以更具体的那一个为准，并在项目 `AGENTS.md` 写一行裁决结论。
- 技能内容变了就重跑一次索引脚本，别手改索引。

## 反模式

- 遇到问题直接开写，写完才发现本地有三个类似技能。
- 装了技能但从不登记，下次还是不知道。
- 把一个项目的一次性脚本包装成"通用技能"，污染索引。
