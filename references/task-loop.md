# 任务循环：一次只做一件事，做完可精确回退

目标有两个：**限制一次改动的影响面**，以及**让"回退"退得动**——不是回退一片，而是回退某一次。

## 一个任务的完整生命周期

```bash
task.py start "把优先级权重改成从 params 读" --files "apps/algo/src/**"
#   → .agent/current-task.json（id / base 提交 / inScope）
#   → .agent/tasks/<id>.log.jsonl（开始时间、目标）

# …改代码、补测试、重建索引…

# 写变更说明（四节，缺一节 finish 就失败）
# .agent/tasks/<id>.md

task.py finish        # 跑门禁 → 汇总改动 → 生成提交信息 → commit
```

`finish` 做四件事：

1. `gate.py all` 必须全绿，否则不提交；
2. 把「改了哪些文件、哪些函数、增删多少行」写进 `.agent/tasks/<id>.json`；
3. 追加一条日志；
4. **提交一次**，信息形如 `task(20261116T153012-优先级权重): 把优先级权重改成从 params 读`，正文带改动清单与验证路径。

一个任务对应一个 commit，这是回退颗粒度的来源。

## 回退：只退一个任务

```bash
task.py revert 20261116T153012-优先级权重
```

按 `task(<id>)` 找提交后 `git revert`，只撤这一个。若后续任务依赖它导致冲突，会明确失败并要人判断——不自动合并，也不强行回滚一片。

## 影响面上限（防止 AI 整块接管）

`finish` 前会算改动指纹，超限则失败：

| 限制 | 默认 | 为什么 |
|---|---|---|
| 单任务文件数 | 15 | 一次碰太多文件，人看不懂也审不动 |
| 单任务符号数 | 20 | 同上，按函数/类计 |
| 整文件重写 | 禁止 | 删除行数 ≥ 原文 60% 且涉及 ≥3 个符号 → 判定重写，要求拆任务 |

Python 用 AST 精确到函数；Java/Rust/C++/JS/TS/Go 按符号起始行近似，**不承诺代码块级**（静态判定代码块不可靠，硬做只会误杀）。

确实需要大重构时：拆成几个任务，或显式提高 `guardrails.json` 的 `task.maxFiles` / `maxSymbols` —— 改配置本身就是一次留痕的决定。

## 变更说明四节

`.agent/tasks/<id>.md` 必须包含：

```markdown
## 改了什么
## 为什么改
## 影响哪些模块
## 如何验证
```

第四节的"如何验证"要写命令和证据路径，不能写"已测试"。门禁只查四节存在，内容是否可信由证据闸门兜底（证据必须有 `paramsHash` 且比源码新）。

## 任务日志

`.agent/tasks/<id>.log.jsonl`，一行一条：

```json
{"at":"2026-11-16T15:30:12+08:00","event":"start","data":{"goal":"...","base":"1f211a3"}}
{"at":"2026-11-16T16:02:44+08:00","event":"finish","data":{"fileCount":3,"symbolCount":5}}
```

出问题时按时间线重放：什么时候开的、改了多大面、验证过什么。比翻聊天记录可靠。

## 为什么有这一层

没有任务边界时，AI 一次会话能改二十个文件；出了问题只能整段回滚，或者再丢给 AI 猜。
有任务边界后，最坏情况是"这一个任务白做"，成本可算、范围可见、责任可追。
